# SpecForge 价值叙事 — API 经济的上游

> 一份面向外部的定位文档：用 OpenAPI 的历史讲清「价值不在规范文件里，在规范的上下游」，并说明 SpecForge 占据的是那个至今空着的、最上游的位置。

---

## 一、一个反直觉的事实：没人靠「卖 OpenAPI 规范」发财

OpenAPI 是整个软件行业最成功的开放标准之一，但它的创始人和核心推动者，**没有一个人靠出售规范本身获得巨额财富**。

**创始人 Tony Tam：从「深夜救急」到加入商业公司。** OpenAPI 的前身 Swagger，是 Tony Tam 于 2010 年在 Wordnik 公司为了解决内部 API 文档问题而创建的，动机非常纯粹甚至「自私」——只是为了摆脱手写文档和客户端的繁重劳动。2015 年 SmartBear 收购了 Swagger 项目，Tony Tam 作为交易的一部分加入 SmartBear，负责 Swagger 产品（含商业版 SwaggerHub）。这笔收购金额从未披露；公开信息里，没有任何证据表明他因此获得巨额个人财富——有资料显示，他如今是苹果公司的云开发者工具工程师。

**真正的商业回报落在了「接手商业化的公司」身上。** SmartBear 收购 Swagger 后保留了品牌与商业产品的控制权，推出 SwaggerHub 等付费工具，把规范的影响力转化为商业收入。OpenAPI 作为行业标准，极大地抬升了 SmartBear 在 API 工具领域的战略地位——2020 年 Francisco Partners 以约 19 亿美元估值收购其多数股权，OpenAPI 资产无疑是其中核心价值的一部分。

**行业巨头投资的是生态，不是标准本身。** 2015 年，SmartBear 将 Swagger 规范捐赠给 Linux 基金会并成立 OpenAPI Initiative（OAI），Google、IBM、Microsoft、PayPal 等成为创始成员。这些公司投入资源参与标准制定，目的并非从标准直接获利，而是塑造有利于自身业务的技术生态。OAI 作为非营利联盟，靠成员年度会员费维持（年收入估计数百万美元量级），资金用于标准维护与推广，而非分配给个人。

**一句话结论：价值没有沉淀在「规范」这个文件里，而是散落在围绕规范生长出来的整个工具与服务生态里。**

这正是基础设施的定价方式——规范越免费、越开放，围绕它的市场越大。

---

## 二、这个故事给我们的启示

OpenAPI 只做了一件事：**标准化了「API 契约长什么样」**。它没有解决、也解决不了另一件更难的事——

**契约从哪里来，以及如何保证它永远新鲜。**

直到今天，OpenAPI 生态里「契约的生产」仍停留在 2010 年的方式：要么靠开发者手写注解（Go 的 swaggo、Java 的 springdoc、Node 的 tsoa），要么靠人工维护一份 spec-first 文档。于是三件事必然发生：

1. 大量存量服务一行注解都没有，补注解的改动量等同于重写接口层；
2. 写了注解的项目，注解与代码随时间漂移，文档比没有更危险；
3. 注解只能描述 handler 函数签名看得见的东西，真实响应体在 service 层深处才被写出，注解表达不了。

**OpenAPI 标准化了「格式」，但没有标准化「生产」。** 规范的生产至今仍是人肉维护的——这是整个生态最大的一块空白，也是价值最集中的地方。

## 三、SpecForge 站在这块空白的上游

SpecForge 做的是**契约的生产层**：给定 `(仓库, 服务名)`，零注解、零侵入地提取真实 HTTP 契约，产出可信、可溯源、确定性的 OpenAPI 3.1，并以「构建系统」的方式做增量分析——改一行代码只重算受影响的那几个事实。

如果说 OpenAPI 是「规范」，SmartBear / SwaggerHub / ReadMe / Stoplight 是规范的「呈现与分发」，那 SpecForge 就是规范的「生产与保鲜」——**比它们更上游的那一环**。SpecForge 的产出，正是这些下游工具的输入。

**我们不打对手，我们打上游。** 市场不是抢来的，SpecForge 站在它们漏斗的上端。

## 四、为什么是现在，为什么是我们

「用 LLM 读代码写 OpenAPI」听起来简单，但朴素的做法有三个结构性缺陷，且不随模型进步而消失：上下文窗口装不下调用图、每次全量重算没有增量、输出不可校验不可信。SpecForge 用四个判断把这些坑一次性封死：

| 判断 | 含义 | 对应的壁垒 |
|---|---|---|
| 这是一条编译流水线，LLM 只是一个 pass | 静态能算准的绝不问模型 | 确定性输出、成本可控 |
| LLM 不产出 YAML，产出「API 事实」 | 事实落进中间表示，由编译器编译成 OpenAPI | 输出稳定、可局部更新、可校验 |
| 增量靠「带动态依赖的记忆化查询引擎」 | 照搬 Salsa 模型，改一行只重算受影响的事实 | 成本随 PR 而非仓库规模增长 |
| 无证据，不成事实 | 每个字段可溯源到 file:line | 幻觉率 <1%，文档可信 |

一句话概括这套系统：**把 LLM 从「文档生成器」降格为「编译流水线里一个可缓存 pass」，用构建系统的严谨性约束模型的不确定性，同时拿到 Agent 的理解力与编译器的确定性与增量能力。**

这带来三个「唯一」：

- 对**存量无注解仓库**，它是唯一能**零改造成本**产出可信文档的路线；
- 对**快速演进的仓库**，它是唯一做到**事实级增量**、成本随 PR 而非仓库规模增长的路线；
- 对 **Agent 时代**，它是唯一把文档升级为**机器可调用证据链**的路线（MCP 形态 + tool 定义导出）。

## 五、价值落在哪

回到开头的故事：OpenAPI 的价值不在「规范文件」里，在生态里。SpecForge 的价值同样不在「又一份 YAML」里，而在它撬动的整个下游：

- **文档平台、SDK 生成、mock 服务**：第一次有了一份「永不过期、字段级可溯源」的输入；
- **AI Agent / IDE**：契约从「给人看的文档」升级为「机器可调用的证据链」，Agent 能直接调用内部 API；
- **API 治理与安全**：破坏性变更检测有了真实基线，而不是凭记忆对账；
- **组织**：存量仓库第一次以接近零成本获得可信契约，文档漂移从根上消失。

技术上可量化的承诺（设计文档验收口径）：

| 指标 | 目标 |
|---|---|
| 路由召回率 | ≥ 98% |
| 请求字段 F1 / 响应字段 F1 | ≥ 95% / ≥ 90% |
| 幻觉率 | < 1% |
| 增量缓存命中率 | 典型 PR ≥ 95% |
| 增量耗时 / 成本 | P90 < 60s，< ¥1 / PR |

> 现状说明：以上为设计目标，核心链路已在单仓 5 服务的真实 Go 仓库（sample-ipo-rebase）上验证——路由召回、确定性双编译自检、契约追踪等均已落地，详见 `README.md` 与 `reports/` 下的验证报告。

## 六、我们的立场

OpenAPI 的创始人证明了一件事：**把最基础的那一层做开放，生态会回报你。** Tony Tam 没靠卖规范发财，但他开创了一个价值数十亿美元的市场。

SpecForge 想做的是下一层同样的事：把「契约的生产」做成开放的基础设施，让规范的上游也免费、也确定、也可信。我们不跟文档平台、SDK 生成器抢生意——我们让它们手里的规范，第一次变得**可信、新鲜、可溯源**。

这是一场关于「上游」的长期主义。
